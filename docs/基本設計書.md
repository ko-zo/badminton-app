# ゆるっとマッチ（組み合わせアプリ）：基本設計書

最終更新：2026-08-21

---

## 1. 概要

バドミントンの練習会で、参加者をコートに割り当てる対戦表を作成するPWA。  
サーバーを持たず、すべてブラウザ内で完結する。データ保存は `localStorage`。

| 項目 | 内容 |
|------|------|
| フロントエンド | HTML / CSS / JavaScript（バニラJS・ライブラリ不使用） |
| ホスティング | GitHub Pages |
| PWA | `manifest.json` + Service Worker（オフライン動作） |
| データ保存 | `localStorage`（端末内のみ・サーバー送信なし） |
| URL | `https://ko-zo.github.io/badminton-app/` |

## 2. 画面構成

スマホ縦画面での片手操作を前提とし、3つのタブで構成する。

| タブ | 役割 | 触る頻度 |
|------|------|---------|
| **メンバー** | 登録簿。過去の参加者を含む全メンバーの台帳 | たまに |
| **試合** | 当日の運用。休憩切り替え・コート設定・組み合わせ | 練習中ずっと |
| **記録** | 試合数・対戦履歴・過去の記録 | 気になったとき |

当日の操作が試合タブだけで完結するよう配置している。

### 2.1 メンバータブ

- 名前入力欄と「追加」ボタン
- 登録済みメンバーの一覧。各行に以下を持つ
  - **性別ボタン**（44px・角丸の四角。タップで − → M → F → − と循環）
    - M：青背景 / F：ピンク背景 / 未設定：白背景
  - **レベルボタン**（44px・**丸**。タップで − → 1 → 2 → 3 → 4 → 5 → − と循環。5が一番上手い）
    - 背景色は性別に追従する
  - 名前
  - **「今回参加する」スイッチ**
  - **削除ボタン**（確認ダイアログを経て削除）

**2つのボタンの形を変えているのは見分けるため。** どちらも未設定だと「−」「−」と同じ表示が並び、色でも文字でも区別できない。

**1つのボタンで「性別×レベル」を全部循環させる案は却下した。** 11状態になり、F3にするのに8タップ必要で、行き過ぎたら一周させ直しになる。分ければ最大5タップで、レベルを直しても性別が消えない。

行の実効幅は375px端末で319px。固定分（44+44+スイッチ+削除+余白）を引いて**名前に残るのは113px**（16pxの日本語で約7文字）。それを超える名前は `…` で省略する。

### 2.2 試合タブ

#### 本日の参加者
- 「今回参加する」がONのメンバーを**名前チップ**で横並び表示
- **チップのタップで休憩をON/OFF**。休憩中は打ち消し線で表示
- 休憩中の人数と抽選対象の人数をヒントに表示

一覧行ではなくチップにしているのは、12人でも3行程度に収まり、コート設定や主ボタンを画面外へ押し出さないため。休憩の切り替えは試合中に頻発するため、組み合わせを作る画面と同じ位置に置いている。

#### 設定
- **コート数**：＋/−ボタンで調整
  - ＋は常にダブルス（4人）を追加するため、**必要人数+4人**の余裕がなければ無効
  - −は最低1コートを維持
- **コート別シングル/ダブルス**：コートごとに個別設定（デフォルト：ダブルス）
- **組み合わせ優先**：**性別と実力の2軸**。それぞれ独立に指定でき、同時に効く

| 行 | 選択肢 | 内容 |
|---|---|---|
| **性別の希望** | 指定なし（既定） / 男女ペア | 男女ペアを優先（ダブルスのみ有効） |
| **実力の希望** | 指定なし（既定） / バランス型 / 同レベル | 4.4 参照 |

- 選んでいる内容の説明を1行表示する（「男女ペア」と「バランス型」は名前だけでは何を混ぜるのか区別できないため）
- 効かない状態・付け忘れをオレンジ色で知らせる
  - 1コートで「同レベル」を選んでいるとき（後述のとおり効果がない）
  - 実力の希望を選んでいて、レベル未設定の参加者がいるとき（人数を表示）

上記の設定は `localStorage` に保存し、起動時に復元する。

#### なぜ2軸にしたか（旧「3択・排他」からの変更）

当初は選択肢を排他の1列に並べていた。理由は「両立できない組み合わせを選べてしまうから」。**実装前に9通り全部をシミュレーションで測った結果、この前提が誤りだった**（`tools/基準の干渉検証.js`）。

| 組み合わせ | 性別の達成 | 実力の達成 |
|---|---|---|
| 男女ペア × バランス型 | 83.0%（単独85.0） | 5.6（単独5.9） |
| 男女ペア × 同レベル | 84.4%（単独85.0） | 36.2（単独35.4） |
| ~~同性対戦~~ × バランス型 | **38.3%**（単独72.9） | 5.4 |
| ~~同性対戦~~ × 同レベル | **14.2%**（単独72.9） | 37.5 |

**衝突していたのは同性対戦だけ。** 同性対戦と同レベルはどちらも「誰と誰を同じコートに入れるか」を決める希望なので、同じ人たちを別の基準で仕分けようとして正面衝突する。男女ペアは「ペアの中身」の希望なので、コートの分け方を奪い合わない。

#### 「同性対戦優先」の廃止

利用実績がなく、単独でも達成率72.9%（6人ずつから8人が出場すると同性だけで4人揃わないラウンドが構造的に出る）、ペア多様性の犠牲も最大（65.7 → 41.8）だった。**削除により衝突する組み合わせがゼロになり、「この組み合わせは選べません」という例外ルールが不要になった。**

保存済みの設定が `same-gender` だった場合は、読み込み時の検証で自動的に「指定なし」へ戻る。

#### 対戦表
- コートごとの対戦カード（ダブルス：ペアvsペア / シングル：1vs1）
- プレイヤー名に性別カラーを表示
- **待機**（コートに入れなかった人）と**希望休憩**を分けて表示

#### 操作ボタン

**一番大きなボタンが常に「次にすべきこと」を示す**という原則で配置する。

| 状態 | 主ボタン（大） | 補助ボタン（小） |
|------|--------------|----------------|
| 組み合わせなし | **組み合わせ作成**（オレンジ） | なし |
| 組み合わせ表示中 | **確定して次の組み合わせへ**（緑） | 引き直す / 取り消し |
| 表示中かつ人数不足 | **確定する**（緑） | 引き直す（無効）/ 取り消し |

この配置の理由は次のとおり。試合が終わった直後にユーザーが考えるのは「次の組み合わせを出そう」であり、一番目立つボタンを押す。以前はその位置に「もう一度シャッフル」があったため、**実施した試合が記録されないまま消える事故**が起きやすかった。主ボタンを押し続けるだけで正しく記録が貯まる形にしている。

記録したくない場合だけ、小さい補助ボタンを意識して選ぶ。

## 3. データ設計

### 3.1 localStorage キー

| キー | 内容 |
|------|------|
| `badminton_v1_members` | メンバー配列 |
| `badminton_v1_settings` | コート構成・性別の希望・実力の希望・選択中のタブ |
| `badminton_v1_log` | `{ sessions, pending }`：対戦ログ（直近100件）と未確定の組み合わせ |

**対戦ログと未確定の組み合わせは必ず1つのキーへまとめて書く。** 別々のキーに分けると、片方の書き込みだけが成功したときに状態が食い違い、次のいずれかが起きるため。

- 記録済みなのに未確定が残る → 再起動後にもう一度確定でき、**同じ試合が二重に記録される**
- 未確定が消えたのに記録されていない → **実施した試合が消える**

旧バージョンの `badminton_v1_sessions` / `badminton_v1_pending` は、起動時に読み込んで `badminton_v1_log` へ移行し、移行に成功したら削除する。

### 保存失敗の扱い

保存は例外を握りつぶさず、失敗を検知して以下を行う。

1. **メモリ上の変更を巻き戻す**（確定・取り消し・記録削除）。画面の状態と保存内容が食い違わないようにするため
2. **画面上部に警告を表示する**。黙って失敗すると「確定したのに保存されていない」ことに気づけないため

保存に成功すると警告は自動的に消える。

### 読み込み時の検証

`localStorage` は利用者や他のスクリプトから書き換えられるため、読み込んだ値の構造を検証する。`rounds` が配列でないセッション、`courts` を持たないラウンドなどは読み込み時に除外し、壊れた値で例外が出ないようにする。

### 3.2 メンバー

```js
{ id, name, active, rest, gender, level }
// gender: 'M' | 'F' | null
// level : 1 | 2 | 3 | 4 | 5 | null   5が一番上手い
```

**読み込み時に `level` を検証し、1〜5の整数でなければ `null` に落とす。** レベル機能より前に登録されたメンバーは `level` を持たないため、ここで `null` になる。`undefined` のまま計算へ流すと点数が `NaN` になり、**エラーも出ないまま減点がすべて効かなくなる**（＝希望を設定しても何も起きない）。

計算のときは、未設定を**真ん中の3として扱う**。0や特別扱いにすると、その人だけが常に強い側／弱い側に固定される。過去に「性別未設定の人が必ず待機になる」不具合を出しており、同じ形の事故を防ぐ。全員が未設定なら全候補が同じ点数になり、結果は「指定なし」と一致する。

#### 設定の移行

旧バージョンは `matchPreference` という1つの値だった。起動時に2つへ引き継ぐ。

| 旧 `matchPreference` | 移行後 |
|---|---|
| `mixed` | 性別＝男女ペア / 実力＝指定なし |
| `same-gender` | 性別＝指定なし / 実力＝指定なし（**廃止のため既定値**） |
| `random`・壊れた値・キー無し | どちらも指定なし |

### 3.3 セッション（練習会 = 1日）

```js
{
  date: '2026-08-06',        // セッションID兼日付（ローカル日付）
  names: { id: '名前' },      // 表示用スナップショット（削除されたメンバー対策）
  rounds: [
    {
      at: 1754...,           // 確定時刻
      courts: [
        { type: 'doubles', pair1: [id, id], pair2: [id, id] },
        { type: 'singles', player1: id, player2: id }
      ],
      waiting: [id, ...],
      resting: [id, ...]
    }
  ]
}
```

- 日付が変わると自動的に新しいセッションが始まる
- 保持は直近100件（1回あたり約5KB。上限5MBに対して十分小さい）
- 古いものから破棄されるが、**破棄されるのは過去日のみ**で当日の集計には影響しない

## 4. ロジック設計

### 4.1 対象者の絞り込み

```
登録簿（全メンバー）
  └─ active = true      →  本日の参加者
       └─ rest = false  →  抽選対象
```

### 4.2 記録のタイミング

**組み合わせを作った時点では記録しない。** 確定操作でのみ記録する。

| 操作 | 記録 |
|------|------|
| 組み合わせ作成 | されない |
| 引き直す | されない（何度でも可） |
| 確定して次の組み合わせへ | **される** |
| 取り消し | されない（破棄） |

未確定の組み合わせは `localStorage` に保存し、アプリを閉じても復元する。ただし日付が変わっていれば破棄する。

### 4.3 誰が出るか（公平性）

**「その人がいた間の取り分に対して、どれだけ足りていないか」が大きい人から順に出場させる。** 同点の中はランダム。

```
値 ＝ 実際の試合数 − その人がいた間に配られるはずだった試合数
```

各ラウンドについて、**抽選対象だった人**（出場＋待機）に「出場枠 ÷ 抽選対象の人数」を配る。いなかったラウンドの分は配られない。

先にシャッフルしてから安定ソートすることで、同点グループ内の順序がランダムになる。

確率的な重み付けではなく実数で決めるため、**同じ人が連続して待機し続けることが構造的に起きない**。12人・2コート・30ラウンドの検証で、全員の試合数が完全に一致した。

集計対象は当日のセッションのみ。日が変わればメンバーも変わるため、過去日と混ぜると不公平になる。

#### なぜ「素の試合数」ではないのか（2026-08-21 修正）

素の試合数で比べると、**途中から参加した人がずっと「最少」のままになり、追いつくまで連続で出場してしまう**（＝先にいた人の待機がその分だけ増える）。

2026-08-19 の版では「まだ一度もプールに現れていない人だけ、基準値としてラウンド数を使う」形で対処していたが、**これは効いていなかった**。参加した次のラウンドで待機に入った時点で「現れた」ことになり、そこから素の試合数（0）に戻るため、結局そこから連続で出続ける。

| 12人2コート・10R後に参加、以降10R | 出場 | 連続出場 | 公平な取り分 |
|---|---|---|---|
| 旧（素の試合数＋初回だけ基準値） | **9回** | **9回連続** | 6.2回 |
| 現行（取り分に対する不足） | 6回 | 2回 | 6.2回 |

**休憩していた人には取り分を配らない。** 配ってしまうと、自分の意思で休んだ分を復帰後に取り返す動きになり、今度はその人が連続出場する。休んだ分は取り返さない、が正しい。

#### 休憩から復帰した1回目だけは優先する

取り分を配らないだけだと、休憩を解除しても不足が0のまま（遅れても進んでもいない位置）なので、**復帰後すぐに出られるとは限らない**。「解除したのに何も起きない」と受け取られるため、**復帰した1回目に限り、不足から `RETURN_PRIORITY`（1000）を引いて確実に先頭へ置く**。

- 通常の不足の値は概ね ±1 に収まるため、1000 を引けば必ず先頭に来る
- **一度出場すれば外れる**（最後に出場したラウンドが、最後に休憩したラウンドを追い越すため）。優先は1回だけで、休んだ分がまとめて戻るわけではない
- 復帰した人が同時に複数いて枠に入りきらなくても、**実際に出場するまで優先が続く**
- **途中から新規参加した人には付けない。** ただし新規参加者の不足はちょうど0になり、「遅れている人」と「進んでいる人」の間に並ぶため、結果として直後のラウンドには入りやすい

以上は `tools/実装の検証.js` に回帰テストとして入れてある（途中参加3件・休憩明け4件・優先枠の有無2件）。

### 4.4 どう組むか（多様性・組み合わせ優先）

出場者が決まったあと、その並び順を決める。候補を200通り生成し、最もスコアの低いものを採用する。

スコア（小さいほど良い）：

| 要素 | 重み | 内容 |
|------|------|------|
| 同じペアの再結成 | **初回30**＋2回目以降3ずつ | 当日すでに組んでいれば30、繰り返すごとに+3 |
| 同じ対戦の再戦 | 1 | 当日すでに対戦した回数 × 1 |
| 性別の希望に反する | 100 | 同性ペア1つにつき（ダブルスのみ） |
| 実力の希望に反する | 100 | 下記 |
| ペア内の開きが足りない | 10 | バランス型のみ。下記 |

**希望の重みが極端に大きいのは意図的**。ユーザーが明示的に選んだ設定なので、重複回避より必ず優先させる必要がある。当初この値が10だったため、履歴が溜まると重複回避の減点が上回って設定が無視される問題があった。

**性別と実力は別々の関数で採点して足す。** 2軸で同時に指定できるため、片方にもう片方を埋め込むと分離できなくなる。

#### 実力の希望の採点

| 希望 | 採点 |
|---|---|
| **バランス型** | \|（ペア1のレベル合計）−（ペア2のレベル合計）\| × 100 ＋ 各ペアの (4 − ペア内のレベル差) × 10 |
| **同レベル** | （コート内の最大レベル − 最小レベル）× 100 |

**バランス型に「ペア内の開き」が要る理由**：釣り合いだけを見ると、**上手い人4人のコートも減点0**になり、同レベルと区別がつかなくなる。開きを入れて初めて「混ぜたうえで釣り合わせる」になる。

**開きの重みだけ10と小さいのも意図的**。強くすると同じペアが固定される。重複回避が勝つのは「同じペアの回数 × 3 が開きの重みを超えたとき」なので、30 だと約10回、**10 なら約4回**で崩れる。

**同レベルは1コートでは効果がない。** 出場者は「試合数の少ない人から」で先に確定するため、1コートだと4人の顔ぶれが決まってしまい、並べ替えても最大−最小が変わらない。黙って効かないのが一番よくないので画面で知らせる。

#### 「まだ組んでいないペア」の優先（初回30）

**基準を増やしたのではなく、既存の「同じペアを避ける」の減点のつけ方を変えただけ**（0,3,6,9 → 0,30,33,36）。初対面かどうかが最も重要で、2回目と3回目の差はそれほど重要ではないため、比例させず最初の1回に段差をつける。

ランダム時は現状のしくみだけで既に上限に達しており（8人25ラウンドで全28通りを網羅）、この変更でも数字は動かない。**効くのはバランス型のときで、ペアの種類が 46.7 → 55.8 に増える一方、対戦の釣り合いは 5.8 → 5.9 とほぼ変わらない。** 100以上にすると同レベルが壊れる（コート幅 35.3 → 43.8）ため30に留める。

#### 候補の作り方（同レベルのときだけ「種」を足す）

ランダム200通りで足りるかはモードによって違う。

| 希望 | ランダム200通りだけ | 種あり |
|---|---|---|
| バランス型 | 6.2 | 6.3（**差なし → 種は作らない**） |
| 同レベル | 35.1 | **26.8** |

バランス型は「コート1つの中で釣り合っているか」という個別の話なのでランダムでも当たる。同レベルは「出場者を何グループに分けるか」という全体の話（12人3コートで5775通り）で、ランダムにはまず当たらない。

そこで**同レベルのときだけ、レベル順に並べた候補を30本用意する**。作り方は、同レベルの人どうしをシャッフルしてからレベル順に安定ソートし、さらに各コートに入る4人の並びをシャッフルする。コート内で並べ替えても最大−最小は変わらないので、**30本すべてが同じ実力スコアになり、その中で重複回避が正しく効く**。

**種を1本にすると新しい不具合が出る。** その1本が毎回勝ってしまい、同じペアが**20ラウンド中15.2回**固定される。ランダム候補は同レベルの点で種に勝てないため、重複回避が働く出番が来ない。30本にすると7.0まで下がる。

役割が分離されている点が重要：**4.3が「誰が出るか」（公平性）、4.4が「どう組むか」（多様性・希望）** で、互いに干渉しない。**レベルは4.3に一切影響させない。** 混ぜると初心者が待機に偏り、公平性が根本から壊れる。9通りすべてのシミュレーションで、試合数の最大差が変わらないことを確認済み。

## 5. 非機能要件

### レスポンシブ・アクセシビリティ
- スマホ縦画面で片手操作できること
- タップターゲットは48px以上を確保
- **ピンチ操作による拡大を禁止しない**（文字を大きくして読みたい利用者のため）
- 補助ボタン（引き直す・取り消し）は枠線で輪郭を示し、白地に対して3:1以上のコントラストを確保する

### 検証可能性

**組み合わせのアルゴリズムは、間違っていても画面上は正常に見える。** 組み合わせは必ず表示されるため、目視では判断できない。実際、この機能の検討中に「種を1本にすると同じペアが固定される」「未組み優先を強くしすぎると同レベルが壊れる」という2つの不具合を、実装前のシミュレーションで検出した。

そのため `tools/` に検証スクリプトを置き、**変更したら数値で確認する**。

| スクリプト | 用途 |
|---|---|
| `実装の検証.js` | **app.js の実物**を読み込んで動かし、効果と公平性を測って合否を出す |
| `組み合わせ検証.js` | レベルの段階数・重みを決めるためのシミュレーション |
| `基準の干渉検証.js` | 性別と実力の希望が干渉しないかの検証 |

`実装の検証.js` は、参加者に**本人にも見えない「真の実力 0〜100」**を持たせ、それを段階に丸めた値でアプリに組ませ、**結果を真の実力で採点する**。段階に丸めたことでどれだけ実力が合わなくなるかが測れる。

### 見読性
- 記録は画面上で内容まで確認できること。**過去の記録は日付をタップすると、その日の試合数と全対戦カードを展開表示する**
- 記録はJSONファイルとして書き出せること

### PWA
- ホーム画面にアイコンを置けること（`manifest.json`）
- **Service Worker によりオフラインで動作すること**
- `manifest.json` の主要項目：アプリ名 / アイコン / テーマカラー / `display: standalone`

#### キャッシュ方式：stale-while-revalidate

1. キャッシュがあれば待たせずに返す（起動が速く、オフラインでも動く）
2. 同時に裏でネットワークから取り直し、成功したらキャッシュを差し替える
3. 差し替わった内容は**次回の起動から**使われる

以前は cache-first で、変更のたびに `CACHE_NAME` を手で書き換えないと修正が利用者に届かなかった。**書き換えを忘れてもエラーが出ないため気づけない**という問題があり、実際に何度も踏んだ。現在の方式では書き換えは不要（全体を強制的に作り直したいときの手段としては引き続き有効）。

クエリ付きのURLはキャッシュ対象外とし、同じファイルが別名で溜まらないようにしている。

### 公開方式
- GitHub Pages（静的ホスティング）
- リポジトリはPublicだが、**個人データはすべて端末内の localStorage にあり、リポジトリにもサーバーにも保存されない**

## 6. 既知の制約

| 項目 | 内容 |
|------|------|
| 更新の反映 | 新しい版が反映されるのは次回の起動時（stale-while-revalidate のため） |
| 端末間の同期 | なし。複数端末で使うと記録が分かれる |
| バックアップ | 記録タブの書き出し（JSON）のみ。自動バックアップはない |
| 日付の切り替わり | 深夜0時をまたぐと別セッションになり、試合数の集計がリセットされる |
