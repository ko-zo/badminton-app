# バドミントン組み合わせアプリ：基本設計書

最終更新：2026-08-06

---

## 1. 概要

バドミントンの練習会で、参加者をコートに割り当てる対戦表を作成するPWA。  
サーバーを持たず、すべてブラウザ内で完結する。データ保存は `localStorage`。

| 項目 | 内容 |
|------|------|
| フロントエンド | HTML / CSS / JavaScript（バニラJS・ライブラリ不使用） |
| ホスティング | GitHub Pages |
| PWA | `manifest.json` + Service Worker（オフライン動作） |
| データ保存 | `localStorage`（端末内のみ・サーバー送信なし） |
| URL | `https://ko-zo.github.io/badminton-app/` |

---

## 2. 画面構成

スマホ縦画面での片手操作を前提とし、3つのタブで構成する。

| タブ | 役割 | 触る頻度 |
|------|------|---------|
| **メンバー** | 登録簿。過去の参加者を含む全メンバーの台帳 | たまに |
| **試合** | 当日の運用。休憩切り替え・コート設定・組み合わせ | 練習中ずっと |
| **記録** | 試合数・対戦履歴・過去の記録 | 気になったとき |

当日の操作が試合タブだけで完結するよう配置している。

### 2.1 メンバータブ

- 名前入力欄と「追加」ボタン
- 登録済みメンバーの一覧。各行に以下を持つ
  - **性別ボタン**（タップで − → M → F → − と循環）
    - M：青背景 / F：ピンク背景 / 未設定：白背景
  - 名前
  - **「今回参加する」スイッチ**
  - **削除ボタン**（確認ダイアログを経て削除）

### 2.2 試合タブ

#### 本日の参加者
- 「今回参加する」がONのメンバーを**名前チップ**で横並び表示
- **チップのタップで休憩をON/OFF**。休憩中は打ち消し線で表示
- 休憩中の人数と抽選対象の人数をヒントに表示

一覧行ではなくチップにしているのは、12人でも3行程度に収まり、コート設定や主ボタンを画面外へ押し出さないため。休憩の切り替えは試合中に頻発するため、組み合わせを作る画面と同じ位置に置いている。

#### 設定
- **コート数**：＋/−ボタンで調整
  - ＋は常にダブルス（4人）を追加するため、**必要人数+4人**の余裕がなければ無効
  - −は最低1コートを維持
- **コート別シングル/ダブルス**：コートごとに個別設定（デフォルト：ダブルス）
- **組み合わせ優先**（3択・排他）
  - **ランダム**：優先なし（デフォルト）
  - **混合優先**：男女ペアを優先（ペアの概念があるダブルスのみ有効）
  - **同性対戦優先**：同性だけのコートを優先（シングルスにも有効）

上記の設定は `localStorage` に保存し、起動時に復元する。

#### 対戦表
- コートごとの対戦カード（ダブルス：ペアvsペア / シングル：1vs1）
- プレイヤー名に性別カラーを表示
- **待機**（コートに入れなかった人）と**希望休憩**を分けて表示

#### 操作ボタン

**一番大きなボタンが常に「次にすべきこと」を示す**という原則で配置する。

| 状態 | 主ボタン（大） | 補助ボタン（小） |
|------|--------------|----------------|
| 組み合わせなし | **組み合わせ作成**（オレンジ） | なし |
| 組み合わせ表示中 | **確定して次の組み合わせへ**（緑） | 引き直す / 取り消し |
| 表示中かつ人数不足 | **確定する**（緑） | 引き直す（無効）/ 取り消し |

この配置の理由は次のとおり。試合が終わった直後にユーザーが考えるのは「次の組み合わせを出そう」であり、一番目立つボタンを押す。以前はその位置に「もう一度シャッフル」があったため、**実施した試合が記録されないまま消える事故**が起きやすかった。主ボタンを押し続けるだけで正しく記録が貯まる形にしている。

記録したくない場合だけ、小さい補助ボタンを意識して選ぶ。

## 3. データ設計

### 3.1 localStorage キー

| キー | 内容 |
|------|------|
| `badminton_v1_members` | メンバー配列 |
| `badminton_v1_settings` | コート構成・組み合わせ優先・選択中のタブ |
| `badminton_v1_log` | `{ sessions, pending }`：対戦ログ（直近100件）と未確定の組み合わせ |

**対戦ログと未確定の組み合わせは必ず1つのキーへまとめて書く。** 別々のキーに分けると、片方の書き込みだけが成功したときに状態が食い違い、次のいずれかが起きるため。

- 記録済みなのに未確定が残る → 再起動後にもう一度確定でき、**同じ試合が二重に記録される**
- 未確定が消えたのに記録されていない → **実施した試合が消える**

旧バージョンの `badminton_v1_sessions` / `badminton_v1_pending` は、起動時に読み込んで `badminton_v1_log` へ移行し、移行に成功したら削除する。

### 保存失敗の扱い

保存は例外を握りつぶさず、失敗を検知して以下を行う。

1. **メモリ上の変更を巻き戻す**（確定・取り消し・記録削除）。画面の状態と保存内容が食い違わないようにするため
2. **画面上部に警告を表示する**。黙って失敗すると「確定したのに保存されていない」ことに気づけないため

保存に成功すると警告は自動的に消える。

### 読み込み時の検証

`localStorage` は利用者や他のスクリプトから書き換えられるため、読み込んだ値の構造を検証する。`rounds` が配列でないセッション、`courts` を持たないラウンドなどは読み込み時に除外し、壊れた値で例外が出ないようにする。

### 3.2 メンバー

```js
{ id, name, active, rest, gender }
// gender: 'M' | 'F' | null
```

### 3.3 セッション（練習会 = 1日）

```js
{
  date: '2026-08-06',        // セッションID兼日付（ローカル日付）
  names: { id: '名前' },      // 表示用スナップショット（削除されたメンバー対策）
  rounds: [
    {
      at: 1754...,           // 確定時刻
      courts: [
        { type: 'doubles', pair1: [id, id], pair2: [id, id] },
        { type: 'singles', player1: id, player2: id }
      ],
      waiting: [id, ...],
      resting: [id, ...]
    }
  ]
}
```

- 日付が変わると自動的に新しいセッションが始まる
- 保持は直近100件（1回あたり約5KB。上限5MBに対して十分小さい）
- 古いものから破棄されるが、**破棄されるのは過去日のみ**で当日の集計には影響しない

## 4. ロジック設計

### 4.1 対象者の絞り込み

```
登録簿（全メンバー）
  └─ active = true      →  本日の参加者
       └─ rest = false  →  抽選対象
```

### 4.2 記録のタイミング

**組み合わせを作った時点では記録しない。** 確定操作でのみ記録する。

| 操作 | 記録 |
|------|------|
| 組み合わせ作成 | されない |
| 引き直す | されない（何度でも可） |
| 確定して次の組み合わせへ | **される** |
| 取り消し | されない（破棄） |

未確定の組み合わせは `localStorage` に保存し、アプリを閉じても復元する。ただし日付が変わっていれば破棄する。

### 4.3 誰が出るか（公平性）

**当日の確定済みラウンドから各メンバーの試合数を集計し、少ない人から順に出場させる。** 同数の中はランダム。

先にシャッフルしてから安定ソートすることで、同数グループ内の順序がランダムになる。

確率的な重み付けではなく試合数そのもので決めるため、**同じ人が連続して待機し続けることが構造的に起きない**。12人・2コート・30ラウンドの検証で、全員の試合数が完全に一致した。

集計対象は当日のセッションのみ。日が変わればメンバーも変わるため、過去日と混ぜると不公平になる。

### 4.4 どう組むか（多様性・組み合わせ優先）

出場者が決まったあと、その並び順を決める。候補を200通り生成し、最もスコアの低いものを採用する。

スコア（小さいほど良い）：

| 要素 | 重み | 内容 |
|------|------|------|
| 同じペアの再結成 | 3 | 当日すでに組んだ回数 × 3 |
| 同じ対戦の再戦 | 1 | 当日すでに対戦した回数 × 1 |
| 組み合わせ優先に反する | 100 | コート単位で判定 |

**組み合わせ優先の重みが極端に大きいのは意図的**。これはユーザーが明示的に選んだ設定なので、重複回避より必ず優先させる必要がある。当初この値が10だったため、履歴が溜まると重複回避の減点が上回って優先設定が無視される問題があった。

役割が分離されている点が重要：**4.3が「誰が出るか」（公平性）、4.4が「どう組むか」（多様性）** で、互いに干渉しない。

## 5. 非機能要件

### レスポンシブ・アクセシビリティ
- スマホ縦画面で片手操作できること
- タップターゲットは48px以上を確保
- **ピンチ操作による拡大を禁止しない**（文字を大きくして読みたい利用者のため）
- 補助ボタン（引き直す・取り消し）は枠線で輪郭を示し、白地に対して3:1以上のコントラストを確保する

### 見読性
- 記録は画面上で内容まで確認できること。**過去の記録は日付をタップすると、その日の試合数と全対戦カードを展開表示する**
- 記録はJSONファイルとして書き出せること

### PWA
- ホーム画面にアイコンを置けること（`manifest.json`）
- **Service Worker によりオフラインで動作すること**
- `manifest.json` の主要項目：アプリ名 / アイコン / テーマカラー / `display: standalone`

#### キャッシュ方式：stale-while-revalidate

1. キャッシュがあれば待たせずに返す（起動が速く、オフラインでも動く）
2. 同時に裏でネットワークから取り直し、成功したらキャッシュを差し替える
3. 差し替わった内容は**次回の起動から**使われる

以前は cache-first で、変更のたびに `CACHE_NAME` を手で書き換えないと修正が利用者に届かなかった。**書き換えを忘れてもエラーが出ないため気づけない**という問題があり、実際に何度も踏んだ。現在の方式では書き換えは不要（全体を強制的に作り直したいときの手段としては引き続き有効）。

クエリ付きのURLはキャッシュ対象外とし、同じファイルが別名で溜まらないようにしている。

### 公開方式
- GitHub Pages（静的ホスティング）
- リポジトリはPublicだが、**個人データはすべて端末内の localStorage にあり、リポジトリにもサーバーにも保存されない**

## 6. 既知の制約

| 項目 | 内容 |
|------|------|
| 更新の反映 | 新しい版が反映されるのは次回の起動時（stale-while-revalidate のため） |
| 端末間の同期 | なし。複数端末で使うと記録が分かれる |
| バックアップ | 記録タブの書き出し（JSON）のみ。自動バックアップはない |
| 日付の切り替わり | 深夜0時をまたぐと別セッションになり、試合数の集計がリセットされる |
