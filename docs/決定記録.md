# 決定記録（ADR）

このアプリとその周辺で行った判断の記録。**「なんでこうしたんだっけ？」に答えるためのもの**であり、実装の細部ではなく、後から理由を問われうる判断だけを残す。

形式は Michael Nygard の ADR を簡略化したもの。

---

## ADR-001 ローカルフォルダは日付あり、GitHubリポジトリ名は日付なし

**日付**：2026-08-05

- **状況**：`Documents\Projects` 配下の命名が統一されておらず、同じアプリのフォルダが2つ並んでいた（`20260414_Badominton_App` と `20260414_badminton-app`）。原因は綴りのtypo
- **決定**：ローカルフォルダは `YYYYMMDD_名前`（kebab-case）。GitHubリポジトリ名は日付を付けない
- **理由**：同じ「名前を決める」でも**可逆性が違う**。ローカルのフォルダ名はいつでもコストゼロで変更できるため、着手日が見える利便性を取ってよい。一方リポジトリ名は公開URL（`ko-zo.github.io/リポジトリ名/`）になり、変更するとPWAのインストールとブックマークが壊れるため、事実上変更できない。日付を入れると永久に残る
- **却下案**：全面的に日付なし。着手日が一目で分からなくなる不便が上回ると判断（当初この案を推奨したが、「重複の原因は日付プレフィックスである」という根拠が誤りだった。実際の原因はtypo）
- **再検討条件**：独自ドメインを使い始め、URLからリポジトリ名が消えたとき

## ADR-002 使わないプロジェクトは削除せず `_archive` へ退避

**日付**：2026-08-05

- **状況**：空フォルダや未着手のプロジェクトが複数あり、一覧の見通しを悪くしていた
- **決定**：削除せず `Documents\Projects\_archive\` へ移動する。日付プレフィックスは維持
- **理由**：判断を誤っても戻せる（可逆性の確保）。整理のたびに削除していると、後から必要になったときに復元できない
- **却下案**：不要なものは削除。判断ミスのコストが非対称（残す不便 << 消す損失）
- **再検討条件**：なし

## ADR-003 リポジトリ名を `badminton-app` に変更

**日付**：2026-08-05

- **状況**：リポジトリ名が `20260414_badminton-app` で、ADR-001 の規則に反していた
- **決定**：`badminton-app` にリネームする。公開URLが変わり、スマホのPWAは再インストールが必要になることを受け入れる
- **理由**：**変更コストが時間とともに上がる決定**だから。この時点では利用者が本人のみで、壊れるのは自分のスマホ1台。将来配布してから変更するコストは比較にならない。安いうちに済ませる
- **却下案**：現状維持。URLに日付が残り続け、後から変更する機会は永久に来ない
- **再検討条件**：なし

## ADR-004 リポジトリは Public のまま運用する

**日付**：2026-08-06

- **状況**：非公開化を検討した
- **決定**：Public のまま運用する
- **理由**：無料プランでは Private リポジトリから GitHub Pages を公開できず、非公開にするとアプリのURLが停止する。さらに**個人データはリポジトリではなく端末の localStorage にある**ため、非公開化による機密性の向上はほぼ無い。失うもの（公開URL、更新の配信、再インストール手段）が得るものを大きく上回る
- **却下案**：Private 化。コード自体を隠したい場合は、Cloudflare Pages や Netlify（無料でPrivateリポジトリから配信可能）へ移す選択肢がある
- **再検討条件**：GitHub Pro 以上に移行したとき、または配信先を変更したとき

## ADR-005 公平化を「試合数ベース」に変更し、重み付け方式を廃止

**日付**：2026-08-06

- **状況**：前ラウンドで待機・休憩した人を3倍の重みで抽選する方式だった
- **決定**：当日の確定済み試合数が少ない人から順に出場させる（同数はランダム）。重み付け方式は削除
- **理由**：重み付けは**確率的**であり、運が悪ければ同じ人が連続して待機する。試合数そのもので決めれば構造的に起きない。検証では12人・2コート・30ラウンドで全員の試合数が完全に一致した（従来方式は最大8試合の差）
- **却下案**：重みを4倍・5倍に上げる。確率である限り連続待機は消えない
- **再検討条件**：なし

## ADR-006 出場者の選定と、並び順の決定を分離する

**日付**：2026-08-05

- **状況**：「混合優先」「同性対戦優先」を選ぶと、**性別未設定のメンバーがほぼ100%待機になっていた**。1200ラウンドの検証で、性別設定済みは一度も待機せず、未設定者が全4800回の待機を占めた
- **決定**：出場者は公平性のみで確定させ、性別による並べ替えは**出場者の中だけ**で行う
- **理由**：原因は、公平に並べた**後**に性別で並べ替えていたこと。並べ替えで性別未設定者が必ず配列の末尾へ回り、コートは先頭から埋まるため構造的に余っていた。**関心の分離**により、公平性（誰が出るか）と好み（どう組むか）が干渉しなくなった
- **却下案**：性別未設定者を中間に挿入する。対症療法であり、優先設定を追加するたびに同じ問題が再発する
- **再検討条件**：なし

## ADR-007 組み合わせ優先の重みを、重複回避より決定的に大きくする

**日付**：2026-08-06

- **状況**：組み合わせの並びをスコアで選ぶ際、優先設定違反の減点が10、ペア重複が3だった。同性対戦優先を選んでも理論上限の半分程度しか達成できていなかった
- **決定**：優先設定違反の重みを100にする
- **理由**：履歴が溜まるとペア重複の減点が積み上がり、**優先設定の減点を上回って逆転**していた。探索回数を200→5000に増やしても改善しなかったことから、探索不足ではなく重み設計の問題と判明。優先設定は利用者が明示的に選んだものなので、重複回避より必ず優先されるべき。変更後は理論上限に完全一致
- **却下案**：探索回数を増やす。検証により無効と確認済み
- **再検討条件**：優先設定の種類を増やすとき

## ADR-008 セッションは日付単位とし、公平性の集計は当日分のみ

**日付**：2026-08-06

- **状況**：試合数を集計するにあたり、過去の練習会の記録と混ざる懸念があった
- **決定**：ローカル日付をセッションIDとし、日付が変わったら自動的に新セッションを開始する。公平性の計算は当日のセッションのみを対象とする
- **理由**：日が変われば参加メンバーが変わる。過去日の試合数を持ち越すと、今日初参加の人が不当に優遇される
- **却下案**：手動でセッションを開始する。開始し忘れが起きる
- **再検討条件**：深夜0時をまたぐ練習会が常態化したとき（現状は未対応で、0時をまたぐと集計がリセットされる）

## ADR-009 過去の記録は直近100件を保持する

**日付**：2026-08-06

- **状況**：保持件数の上限を決める必要があった
- **決定**：練習会100回分を保持し、超過分は古い順に破棄
- **理由**：1回あたり約5KB、100回で約0.5MB。localStorage の上限5MBに対して十分小さい。週1回の練習で約2年分。当初20件で検討したが、根拠なく少なすぎた
- **却下案**：無制限。上限がないと際限なく増える可能性を残す
- **再検討条件**：破棄が実際に発生し、失われて困ったとき（現状は**破棄が無言**で行われる点が保存性の課題として残っている）

## ADR-010 記録は「確定」操作でのみ行う

**日付**：2026-08-06

- **状況**：組み合わせを作った時点で記録していたため、作ってみて実施しなかったラウンドも実績に残り、公平性の計算が狂っていた
- **決定**：組み合わせの作成・引き直しでは記録せず、確定操作でのみ記録する
- **理由**：**組み合わせを作ることと、試合をすることは別の事象**。記録すべきは後者。これにより気に入るまで引き直しても実績が汚れない
- **却下案**：なし（問題の指摘と同時に方針が確定）
- **再検討条件**：なし

## ADR-011 主ボタンを常に「次にすべきこと」に固定する

**日付**：2026-08-06

- **状況**：組み合わせ表示中、画面で一番目立つ大きなボタンが「もう一度シャッフル」だった。試合後は「次の組み合わせを出そう」と考えるため、そのボタンを押しやすく、**実施した試合が記録されないまま消える**事故が起きやすかった
- **決定**：主ボタンの意味を状態で切り替える。組み合わせなし＝「組み合わせ作成」、表示中＝「確定して次の組み合わせへ」。引き直す・取り消しは小さい補助ボタンとして下段へ
- **理由**：**レイアウトが誤操作へ誘導していた**（ニールセン「エラーの防止」）。主ボタンを押し続けるだけで正しく記録が貯まる形にすれば、間違った操作は小さいボタンをわざわざ選ばない限り起きない
- **却下案**：**組み合わせ作成から5分経過したら自動確定する。** 時間は「試合をした」の代理指標として弱く（コート待ち、相談中、解散後にも経過する）、しかも自動確定は画面を見ていないときに起きるため**誤りに気づけない**。押し忘れという静かな故障を、誤記録という別の静かな故障に置き換えるだけで、データの信頼性を損なう
- **再検討条件**：レイアウト変更後も押し間違いが実際に発生したとき

## ADR-012 記録と未確定の組み合わせを1つのキーに統合する

**日付**：2026-08-06

- **状況**：`badminton_v1_sessions` と `badminton_v1_pending` の2キーに分けて保存しており、確定処理が2回の書き込みに分かれていた
- **決定**：`badminton_v1_log` に `{ sessions, pending }` としてまとめ、1回の書き込みで保存する。旧キーからは起動時に自動移行
- **理由**：片方だけ成功すると状態が食い違う（**原子性の違反**）。記録済みなのに未確定が残れば再起動後にもう一度確定でき**試合の二重計上**、逆なら**実施した試合の消失**が起きる
- **却下案**：書き込み順序を工夫する。順序を変えても2回に分かれている限り中間状態は生まれる
- **再検討条件**：なし

## ADR-013 保存失敗を検知し、巻き戻して警告する

**日付**：2026-08-06

- **状況**：すべての保存処理が `try { ... } catch {}` で例外を捨てていた
- **決定**：失敗を検知してメモリ上の変更も巻き戻し、画面上部に警告を表示する。保存に成功すると警告は消える
- **理由**：**気づけない失敗は、目に見える失敗より常に悪い**。従来は「確定したように見えるのに保存されていない」状態になり、エラーも出ないため気づけなかった。巻き戻すことで、画面の状態と保存内容が常に一致する
- **却下案**：警告のみ表示して巻き戻さない。画面と実データが食い違ったままになる
- **再検討条件**：なし

## ADR-014 本日の参加者を試合タブへ移し、チップ表示にする

**日付**：2026-08-06

- **状況**：休憩の切り替えをメンバータブに置いていたが、試合中に頻発する操作のためタブ間の往復が必要だった
- **決定**：メンバータブは登録簿（全メンバーの台帳）のみとし、本日の参加者と休憩切り替えは試合タブへ移す。一覧行ではなく名前チップにする
- **理由**：**触る頻度と配置を一致させる**。当日の運用が試合タブだけで完結する。一覧行だと12人で12行を占め、コート設定や主ボタンを画面外へ押し出すため、チップにして3行程度に収めた
- **却下案**：両方のタブに置く。同じ操作が2箇所にあると、どちらが正か分からなくなる
- **再検討条件**：なし

## ADR-015 過去の記録を画面上で展開表示できるようにする

**日付**：2026-08-07

- **状況**：過去の記録は日付とラウンド数しか表示されず、内容を確認するには JSON を書き出して自力で読むしかなかった
- **決定**：日付をタップすると、その日の試合数と全対戦カードを展開表示する
- **理由**：**見読性**（電子保存の三原則）を満たしていなかった。「エクスポートすれば読める」は要件を満たさない。アプリを開いて確認できることが必要
- **却下案**：別画面へ遷移する。1階層増やすほどの情報量ではない
- **再検討条件**：1日のラウンド数が多くなり、展開表示が長すぎると感じたとき

## ADR-016 Service Worker を stale-while-revalidate 方式に変更する

**日付**：2026-08-07

- **状況**：cache-first 方式のため、変更のたびに `CACHE_NAME` を手で書き換えないと修正が利用者に届かなかった。書き換えを忘れてもエラーは出ず、デプロイも成功するため気づけない。この開発期間だけで v2〜v9 まで8回書き換え、実際に開発中も古いファイルを掴む事故が複数回発生した
- **決定**：キャッシュがあれば即座に返し、同時に裏でネットワークから取り直してキャッシュを差し替える。反映は次回起動時
- **理由**：**注意力に依存した運用をやめる**（ポカヨケ）。「書き換えを忘れないよう気をつける」は対策ではない。仕組み自体が新しさを確認する形にすれば、忘れようがない。オフライン動作と起動の速さは維持される
- **却下案1**：ネットワーク優先。確実だが、電波の悪い体育館で起動が遅くなる
- **却下案2**：Service Worker を削除。オフラインで使えなくなり、体育館という利用場面に合わない
- **再検討条件**：起動時の通信量が問題になったとき

## 未対応として認識している課題

決定はしていないが、点検で見つかり保留にしているもの。

| 課題 | 観点 | 内容 |
|---|---|---|
| 記録削除の痕跡 | 真正性 | 削除しても痕跡が残らない。取り消し線で残す方式が望ましい |
| 端末時計への依存 | 真正性 | 記録時刻とセッション日付が端末の時計に依存する |
| 100件超過時の無言破棄 | 保存性 | 破棄されたことに気づけない |
| 書き出し形式 | 見読性 | JSONのみで、表計算ソフトや印刷に向かない |
| 複数タブでの上書き | 独立性 | 同時に開くと後勝ちで記録が消える。検知していない |
| 同一オリジンの共有 | 機密性 | 同じアカウントで別サイトを公開すると、データが読み取り可能になる |
| 深夜0時をまたぐ運用 | — | セッションが分割され、試合数の集計がリセットされる |
| 色のみによる性別表示 | WCAG | 対戦表と待機チップは背景色だけで性別を示している |
| 同名メンバーの区別 | UX | 画面上は名前のみで、同姓同名を区別できない |
